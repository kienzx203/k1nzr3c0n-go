# k1z store on PostgreSQL

The k1nzr3c0n workflow-runner half of the binary (package `k1z/store`) can now
run on **PostgreSQL** as well as SQLite. SQLite stays the default; PostgreSQL is
an explicit opt-in. The ARTEX half already runs on PostgreSQL, so opting in lets
both halves share one database server.

## Opting in

Set **`K1Z_PG_DSN`** to a PostgreSQL DSN and restart:

```sh
export K1Z_PG_DSN='postgres://user:pass@host:5432/dbname?sslmode=disable'
```

- Unset (the default) → the store uses the SQLite file at `config.DBPath()`
  (`k1nzr3c0n.db`), exactly as before.
- Set → the store opens PostgreSQL via the pgx `database/sql` driver.

To run **both halves on one database**, set `K1Z_PG_DSN` to the same value as
`ARTEX_PG_DSN`. The k1z tables live in their own `k1z` schema (see below), so
they never collide with the ARTEX tables in `public`.

> **Safety:** there is deliberately **no implicit fallback to `ARTEX_PG_DSN`**.
> Every ARTEX install already sets `ARTEX_PG_DSN`; if k1z adopted it
> automatically, an existing install would silently abandon its `k1nzr3c0n.db`
> for an empty PostgreSQL schema on the next restart. You must opt in explicitly.

On boot the backend logs which backend it chose:

```
[k1z] store backend: PostgreSQL (schema k1z, via K1Z_PG_DSN)
[k1z] store backend: SQLite (/opt/k1nzr3c0n/data/k1nzr3c0n.db)
```

## How it works

A thin **dialect layer** (`k1z/store/dialect.go`, `schema_pg.go`, `open_pg.go`)
keeps a single SQLite source of truth and adapts it to PostgreSQL at open time,
so the ~215 query call sites are untouched:

| Concern | SQLite | PostgreSQL |
| --- | --- | --- |
| Placeholders | `?` | `$1, $2, …` (rebound by `xdb`) |
| Auto-increment id | `LastInsertId()` | `INSERT … RETURNING id` (`insertReturningID`) |
| Schema namespace | the file | a dedicated `k1z` schema (`search_path`) |
| `AUTOINCREMENT` | `INTEGER … AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| `DATETIME` columns | `DATETIME` (text) | `TEXT` — time stays text (`SqlTime`/`ParseTime`), unchanged behavior |
| `DEFAULT CURRENT_TIMESTAMP` | native | `to_char(now()…)` in the app's own time format |
| `BOOLEAN DEFAULT 0/1` | native | `DEFAULT FALSE/TRUE`; booleans stay native |
| `INSERT OR IGNORE` | native | `INSERT … ON CONFLICT DO NOTHING` |
| `ALTER TABLE ADD COLUMN` | ignore dup-column error | `ADD COLUMN IF NOT EXISTS` |

The `k1z` schema is created at init (`CREATE SCHEMA IF NOT EXISTS k1z`) and
pinned as `search_path = k1z, public` on every pooled connection, so all
unqualified table names resolve to it.

## What is NOT automatic

- **No data migration.** A fresh PostgreSQL starts empty; existing SQLite data
  is not copied. Moving data would need an export/import (not built — the schema
  matches column-for-column, so a per-table dump/load is feasible if needed).
- **Backup/restore endpoints** (`/api/v1/system/backup` …) snapshot the SQLite
  file. On PostgreSQL use `pg_dump --schema=k1z` instead.
- **The traffic-capture store** (`traffic/traffic.go`) is a *separate* SQLite
  database (per-run HTTP capture, ~20 queries / 3 tables) and still uses SQLite.
  It can be migrated the same way later if desired; it is lower priority because
  the data is ephemeral per run.

## Testing against a real PostgreSQL

`TestPostgresEndToEnd` (in `k1z/store`) is skipped unless `K1Z_PG_DSN` is set, so
the normal (SQLite) test run is unaffected. To run it:

```sh
docker run -d --name k1zpg -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=k1ztest \
    -p 55432:5432 postgres:16-alpine
K1Z_PG_DSN='postgres://postgres:pw@127.0.0.1:55432/k1ztest?sslmode=disable' \
    go test ./k1z/store/ -run TestPostgresEndToEnd -v
docker rm -f k1zpg
```

This creates the 37 k1z tables in the `k1z` schema and exercises IDENTITY
inserts, BOOLEAN round-trips, the timestamp default, and INSERT-OR-IGNORE
seeding.
